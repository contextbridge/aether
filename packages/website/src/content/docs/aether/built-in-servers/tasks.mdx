---
title: Tasks
description: Hierarchical task management for long-running agent work.
---

The `tasks` server gives agents a structured way to decompose work into task trees, dependencies, assignees, status, and handoff metadata.

## Configuration

The default in-memory server is session-scoped: tasks are stored in a temporary directory and cleaned up when the server exits.

```json title=".aether/mcp.json"
{
  "servers": {
    "tasks": {
      "type": "in-memory"
    }
  }
}
```

For persistent task storage, pass `--dir`. Aether stores each root task tree as a JSONL file under `<dir>/.aether-tasks/active/`; when a tree is completed it is moved to `<dir>/.aether-tasks/completed/`.

```json title=".aether/mcp.json"
{
  "servers": {
    "tasks": {
      "type": "in-memory",
      "args": ["--dir", "."]
    }
  }
}
```

## Tools

| Tool          | Description                                                              |
| ------------- | ------------------------------------------------------------------------ |
| `task_create` | Create a root task tree or subtask.                                      |
| `task_get`    | Get full details for one task by ID.                                     |
| `task_list`   | List tasks, optionally filtered by assignee, status, tree, or readiness. |
| `task_update` | Update status, ownership, dependencies, or handoff metadata.             |

## Task IDs

- Root tasks: `at-a1b2c3d4`
- Subtasks: `at-a1b2c3d4.1`, `at-a1b2c3d4.2`, etc.

Each root task tree is stored in one JSONL file when persistent storage is enabled. Archiving a completed tree moves its file from `active/` to `completed/`.

## Status values

| Status       | Meaning                    |
| ------------ | -------------------------- |
| `pending`    | Not yet started.           |
| `inProgress` | Currently being worked on. |
| `completed`  | Done.                      |
| `blocked`    | Not ready to proceed.      |

`in_progress` is accepted as an input alias for `inProgress`.

## Listing and filtering

`task_list` accepts optional filters:

| Field       | Type      | Description                                                                          |
| ----------- | --------- | ------------------------------------------------------------------------------------ |
| `assignee`  | `string`  | Only return tasks assigned to this agent or worker.                                  |
| `status`    | `string`  | Filter by status: `pending`, `inProgress`, `completed`, or `blocked`.                |
| `treeId`    | `string`  | Only return tasks in one tree, identified by its root task ID.                       |
| `readyOnly` | `boolean` | Only return tasks that are ready to start (pending with all dependencies completed).  |

## Examples

Create a root task:

```json title="task_create"
{
  "title": "Refresh website docs",
  "description": "Update public docs from Rust source facts.",
  "assignee": "orchestrator"
}
```

Create a subtask with a dependency:

```json title="task_create"
{
  "title": "Validate docs build",
  "parentId": "at-a1b2c3d4",
  "assignee": "worker-1",
  "deps": ["at-a1b2c3d4.1"]
}
```

List ready work:

```json title="task_list"
{
  "readyOnly": true
}
```

Complete a task and attach handoff context:

```json title="task_update"
{
  "id": "at-a1b2c3d4.1",
  "status": "completed",
  "summary": "Updated MCP configuration docs from source.",
  "facts": ["Tool filters support exact names and trailing * only."],
  "nextSteps": ["Run website checks."],
  "filesRead": ["crates/mcp-utils/src/client/config.rs"]
}
```

## Handoff fields

`task_update` accepts an `id` plus any combination of fields to change. In addition to `title`, `description`, `status`, `assignee`, and `deps`, you can attach handoff metadata:

| Field       | Purpose                                 |
| ----------- | --------------------------------------- |
| `summary`   | Short summary of work done or findings. |
| `decisions` | Key decisions made.                     |
| `facts`     | Important facts discovered.             |
| `nextSteps` | Suggested follow-up actions.            |
| `blockers`  | Unresolved blockers.                    |
| `filesRead` | Files examined.                         |
| `resources` | External resources referenced.          |

`task_update` returns the updated task, a `message`, the list of field names in `changes`, and `newlyReady` — the tasks that became ready to start because their dependencies were completed.

## Input names

The canonical MCP wire format is camelCase: `parentId`, `treeId`, `readyOnly`, `nextSteps`, and `filesRead`. The server also accepts snake_case aliases for several inputs, including `parent_id`, `tree_id`, `ready_only`, `next_steps`, and `files_read`.
